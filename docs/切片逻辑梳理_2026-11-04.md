# 当前切片逻辑梳理与 Web 展示设计基线

- 整理日期：2026-11-04
- 依据：当前仓库中的 `processor.py`、`cut_manager.py`、`cut_preview.py`、`render_generic.py`、`content_fingerprint.py`、`upload_manager.py`，以及当前磁盘成片和指纹库的只读核验
- 目标：先以现有实现为准建立唯一事实基线，再据此重构 Web 工作台；本文不修改切片算法

---

## 1. 结论先行

当前切片链路可以概括为：

```text
素材剧集
  -> 集号扫描与副本去重
  -> ASR 逐集转写
  -> LLM 高光候选 / 关键词兜底
  -> 非重叠 20 秒窗口化
  -> 导演方案（不同开头集、角度标签、叙事顺序）
  -> 每版挑选约 10 个片段
  -> EDL 配置
  -> 逐片段裁剪并拼接
  -> 一次性视觉/音频“抗查重”滤镜
  -> 帧指纹版本间去重
  -> 媒体质量门禁、QC、交付报告
  -> 同账号已入队/已上传内容查重
  -> 上传到视频号草稿箱
```

当前被视频号判定“与已发表视频高度相似”，主要不是上传按钮或单个 ffmpeg 参数的问题，而是以下三层偏差：

1. **当前实现优化的是“片段不完全相同”，平台判断的是“作品内容和来源是否实质相同”。**
   同一部剧的不同集、不同 20 秒片段，画面哈希可以完全不同，但对平台来说仍可能是同一部作品的原声连续片段。
2. **当前本地指纹没有平台已发表内容这个比较库。**
   指纹查重只比较本机生成的成片和同账号已入队/已上传记录，无法知道平台上其他账号已经发表了什么。
3. **多版本仍使用同一部剧的原画面、原对白和原音轨。**
   当前“抗查重”主要是 1.05 倍速、上下裁切、调色、噪点、微旋转、音频 EQ、动态水印。这些改变的是像素和编码表现，不改变内容语义，不能作为“原创作品”的核心依据。

当前成片的实测也支持这个判断：

| 剧名 | 版本数 | 全部片段数 | 精确重复片段 | 本地帧指纹平均/最高相似度 |
|---|---:|---:|---:|---:|
| 猛虎护我归来 | 8 | 80 | 0 | 0.001 / 0.010 |
| 揭穿英国假贵族 | 8 | 80 | 0 | 0.002 / 0.016 |
| 小渔女成了全家的宝 | 8 | 80 | 0 | 0.001 / 0.010 |
| 年薪百万救不起亲妈 | 8 | 80 | 6 | 0.008 / 0.204 |

这些版本在本地算法下几乎“不重复”，但平台仍会认为它们是同一剧集中连续摘取的内容。因此，现有本地相似度不能代表平台原创度。

## 2. 当前切片链路

### 2.1 入口与任务管理

| 项目 | 当前实现 |
|---|---|
| 素材来源 | 默认 `E:\短剧素材` |
| 可选剧条件 | 递归扫描后，按集号去重，至少存在 2 个 MP4 |
| 任务入口 | Web「批量切片」页勾选剧名，逐条加入任务 |
| 任务存储 | `data/jobs.db` 的 `cut` 类型任务，可跨服务重启恢复 |
| 页面默认账号 | 固定提交 `小桃追剧中` |
| 实际输出账号 | 由服务端 `CONFIG.upload_account` 再推导，页面提交值不能代表最终账号 |
| 暂停 | 当前任务继续执行，处理完当前剧后暂停后续队列 |
| 停止 | 协作式取消 ASR、渲染子进程；当前任务回到 pending |
| 恢复 | `resume=true` 优先读取已保存的 `edl_config_v*.json` 只重渲染 |

当前页面只显示待切片、切片中、完成、失败四个计数，以及任务状态和一段日志。它没有展示 ASR、高光规划、选段、EDL、渲染、质量门禁、内容风险等阶段的信息。

### 2.2 素材整理与 ASR

1. 通过文件名解析集号，递归查找 MP4；同一集存在多份副本时优先保留路径更浅的一份。
2. 对每集执行 ASR，转写缓存放在素材目录的 `transcribe/EP<集名>.json`。
3. 转写片段包含单集内相对时间、句首、句尾和文本。
4. 若 ASR/转写不可用，后续高光数据为空时可能回退到随机分段。

### 2.3 高光候选与 20 秒窗口化

1. 主路径逐集调用 LLM，返回 1-3 个高光窗口，字段包括分数、理由、类型和时间句索引。
2. 结果缓存到 `transcribe/highlight_scores.json`；已有缓存时不再重新调用 LLM。
3. LLM 失败时用关键词打分兜底，冲突词权重 2、悬念词权重 1。
4. 当前方案 B 会把候选重排成固定的非重叠时间栅格：从 0 秒开始，每 `segment_dur=20` 秒一段，直到该集尾部不足 20 秒。
5. 固定栅格段会继承排序后候选的分数/类型/理由，但不是按“原候选时间窗与栅格段的重叠”逐段匹配。也就是说，标签可能描述的是高光句，实际选中的 20 秒窗口不一定完整覆盖该高光句子。
6. 每集候选段都进入后续版本选择池，总容量约为 `Σ floor(集时长 / 20)`。

### 2.4 版本数量和导演方案

版本数量规则：

- 素材集数 `>=30`：期望 8 版。
- 素材集数 `<30`：期望 6 版。
- 方案 B 会计算素材容量，但当前实现为了保证 6/8 版，不严格按容量降版本；容量不足时允许受控复用。

导演方案当前包含：

| 字段 | 含义 | 是否真正改变内容 |
|---|---|---|
| `opening_ep` | 每版不同开头集 | 会改变开头素材 |
| `angle` | 逆袭、真相、打脸等标签 | 主要改变文案、文件名和选候选优先级，不直接约束剧情语义 |
| `order_type` | `reverse` / `flashback` / `forward` | 只改变集号顺序；当前 reverse 与 flashback 的排序实现相同 |

规划后会经过一次 Reviewer 审稿，5 个维度分别评估钩子、结构、反转、节奏和情绪。分数低于阈值时带反馈重试，最多重试 2 次；审稿失败会放行，不阻塞切片。

### 2.5 每版片段选择

正式路径以导演方案为主：

1. 从该版 `opening_ep` 所在集选择一个候选作为开头钩子。
2. 其它集按 `head -> 前面集 -> 后面集` 排序。
3. forward 为时间顺序；reverse/flashback 为 `开头集 -> 前面集倒序 -> 后面集顺序`。
4. 每集按版本号轮换一个候选段。
5. 每版计划总时长 200 秒，最短片段 15 秒。
6. 切点若距离 scene 边界不超过 0.15 秒，就吸附到最近镜头边界。
7. 跨版本用 `(集号, 起点)` 做精确去重，同一个时间窗最多复用一个版本。
8. 全局池不足时，补足逻辑允许复用已用片段；当前上限为每版目标片段数的 90%。按 10 段/版计算，理论上后段版本最多可有 9 段复用已有素材。

因此，当前实现存在两个不同概念：

- “精确片段复用”通常很低，甚至在多数已生成剧里为 0。
- “同剧、同角色、同对白、同剧情”的语义复用仍然很高。

### 2.6 EDL 配置

每版写入一个 `edl_config_vN.json`，关键结构为：

```json
{
  "drama_name": "剧名",
  "source_dir": "素材目录",
  "source_pattern": "剧名 - 第{ep}集.mp4",
  "output_dir": "输出目录",
  "artifacts": {
    "video_path": "输出成片路径",
    "cover_path": "封面路径"
  },
  "videos": [{
    "id": 1,
    "hook_keyword": "真相",
    "title": "发布短标题",
    "description": "发布描述",
    "hashtags": [],
    "segments": [
      {"episode": 3, "start": 40.0, "duration": 20.0}
    ]
  }]
}
```

当前 Web 的“方案预览”已经能读取版本、片段来源、入出点、时长、钩子、理由和成片状态，但这是事后查看，不是切片执行过程的实时视图。

### 2.7 渲染

单版渲染步骤：

1. 校验源文件和每个时间码不超出素材真实时长。
2. 若配置了 BGM，尝试把切点吸附到音乐节拍。
3. 每段单独渲染为 1080×1920，等比缩放后黑边补齐。
4. 使用 concat demuxer 拼接；失败再回退 concat filter。
5. 对拼接裸片应用一次视频/音频“抗查重”链。
6. 核验产物：文件大小、视频流、音频流、时长、1080×1920 分辨率。
7. 临时文件写到 `.mp4.tmp`，核验通过后原子改名为最终成片。

当前默认视觉链：

```text
1.05 倍速
裁切为 1080×1860 后补回 1080×1920
对比度 1.05 / 饱和度 1.1 / 亮度 0.02
动态噪点 8
旋转 0.008
每 3 秒切换位置的半透明账号水印
```

当前默认音频链：

```text
1.05 倍速
3000Hz 增益 3dB
100Hz 衰减 2dB
loudnorm -14 LUFS / TP -1 / LRA 11
```

没有做的事项：

- 没有重新生成对白或旁白。
- 没有改变原剧情语义。
- 没有默认加入解说、字幕、原创片头片尾或额外授权素材。
- 没有音频指纹比对。
- 没有和平台已发表视频比对。

### 2.8 成片筛选与三重防重

#### 第一层：时长与质量

- 媒体质量控制：最短 180 秒、最长 300 秒。
- 最佳版本筛选优先选择 210-300 秒；合格数量少于 6 时，会用其它版本补齐。
- 不合格版本会重命名为 `_REJECTED.mp4` 保留，不再直接删除。

#### 第二层：版本间帧指纹

- 每秒采样一帧，缩放到 64×64 灰度。
- 每帧计算 56 位 dHash。
- 两版之间通过短序列在长序列中滑动，计算视觉高度重合的最大比例。
- 默认硬阈值 0.75，软阈值 0.5，最少交付 3 版。
- 指纹异常时保守放行。

局限：

- 只能识别“相同视觉片段”，无法识别“同一部剧的不同片段”。
- 1fps 采样会漏掉短镜头和快速剪辑。
- 没有对白文本、音色、原声、人物、场景和剧情语义比较。
- 版本不同但同源内容可能得到接近 0 的相似度。

#### 第三层：上传前内容查重

- 上传前重新计算成片指纹。
- 只查询同一账号下已上传或当前已入队/上传中的成片。
- 相似度默认阈值 0.6，命中则拒绝入队。
- 跨剧也会命中，但只在同一账号范围内。

局限：

- 不查询另一个账号的本地记录。
- 不查询视频号平台已发表内容。
- 不查询素材库原片。
- 指纹计算失败或数据库异常时放行。

### 2.9 交付与上传

1. 写交付报告，包含版本、片段、账号、内容去重结果。
2. 生成 QC 报告，检查黑帧、响度、词中切断；QC 目前是审计项，不是硬门禁。
3. 写入素材目录 `已切完.txt`。
4. 上传页扫描 `output/<账号>/<剧名>/*_去重版.mp4`。
5. 上传入队同时计算内容指纹，按同账号已发表/已入队内容查重。
6. 上传成功后登记指纹为已上传。

## 3. 当前实现与平台判重的主要错位

### P0：把“画面不同”当成“作品不同”

当前成片由同一部剧的原片直接裁剪、拼接。即使每版使用不同集、不同时间窗，原声、人物、剧情和镜头语言仍来自同一作品。平台的内容相似判断很可能同时使用画面、音频、文本、账号历史或版权/重复库；只改像素表现无法保证原创性。

### P0：比较范围不包含平台已发表内容

本机指纹库不知道平台上已经存在什么。当前查重只能避免“本机同账号重复上传”，不能避免“别的账号已经发过同一剧的这一段”。

### P1：角度标签没有真正控制内容

`angle` 决定文案、文件名、开头候选和候选排序，但不会约束“这一版只讲某条角色线/某个矛盾”。同一批高光被重新排序后仍可挂上不同标签，因此版本看起来不同，实际讲述高度重合。

### P1：叙事顺序实际变化有限

`reverse` 和 `flashback` 当前生成相同集号顺序，只有 `forward` 不同。多个版本主要差异是开头集和局部候选，平台比较整条视频时仍容易识别为同作。

### P1：本地帧指纹对“同源不同片段”失明

当前 8 版同剧内容的本地相似度大多接近 0，但平台上仍判相似。这说明不能继续用 dHash 阈值作为主要验收条件。

### P1：版本数量目标过高，倒逼复用

默认追求 6/8 版，但 30-50 集素材的有效独立内容有限。当前代码允许在补足阶段复用最高 90% 片段。即使当前多数成片尚未出现精确重复，后续素材容量不足时仍会自然产生高重复版本。

### P2：高光窗口与固定 20 秒栅格不完全对齐

LLM 识别的是语义高光窗，后续改为从 0 秒等距切 20 秒的栅格；分数和类型是按排序后的候选顺序套入，并未严格按时间重叠映射。时间轴展示时会出现“选段理由”和实际片段内容不完全对应的问题。

### P2：Web 页面看不到真正的切片决策

当前页面只有任务状态和事后 EDL 预览，没有展示：

- 当前处于 ASR 还是高光规划；
- 每版为什么选择这些集和片段；
- 跨版本复用了多少素材；
- 原声/文本/画面分别有多少重合；
- 具体触发了哪项原创风险；
- 某个版本为何被拒绝或建议减少版本数量。

## 4. Web 工作台建议展示结构

页面不应只展示“进度百分比”，而应把切片拆成可审计的四层。

### 4.1 第一层：任务与版本预算

展示：

- 剧名、素材目录、总集数、总时长、实际可识别集数；
- 计划账号、水印账号、输出目录；
- 期望版本数与“可安全生成的版本数”；
- 为什么是这个版本数：独立镜头容量、语言内容容量、允许复用上限；
- 是否续跑、是否强制重切、是否已有 EDL/成片。

### 4.2 第二层：切片流水线时间轴

建议展示 8 个阶段：

```text
素材扫描 -> ASR -> 高光/语义分析 -> 版本方案 -> 选段与EDL
-> 片段渲染 -> 拼接与后处理 -> 质量/原创风险门禁 -> 可上传
```

每一阶段显示状态、耗时、进度、当前集/版本、输入输出数量、异常与可恢复动作。阶段状态必须来自后端真实事件，而不是前端根据任务状态猜测。

### 4.3 第三层：版本差异矩阵

每一版一行，至少展示：

| 字段 | 说明 |
|---|---|
| 版本号/标题/钩子 | 当前实际发布文案 |
| 开头集 | 实际开头来源 |
| 顺序 | forward / reverse / flashback 的真实结果 |
| 计划/实际时长 | EDL 与成片差异 |
| 片段数 | 当前通常约 10 段 |
| 集覆盖 | 使用了哪些集，是否集中在少数集 |
| 画面重合 | 与其它版本的视觉重合比例 |
| 对白重合 | 原声台词文本 n-gram 重合比例 |
| 音频重合 | 原声音频指纹重合比例 |
| 同源码比例 | 当前版本中来自同一原剧的占比 |
| 风险等级 | 低/中/高，并显示命中的具体规则 |
| 产物状态 | 规划、渲染中、通过、拒收、人工复核 |

### 4.4 第四层：单版故事板

点击一个版本后展示：

- 纵向时间轴，每段标注“第几集、入点、出点、时长”；
- 每段的台词摘要、高光理由、实际匹配的候选窗口；
- 是否存在跨版本复用、复用来自哪一版；
- 缩略帧/片段预览；
- 最终成片的时长、分辨率、音频、文件状态；
- 风险问题定位到具体时间段，而不是只给一个总分。

### 4.5 页面必须避免的误导

- 不把 `已生成 8 版` 当成 `已有 8 个可安全发布版本`。
- 不把 dHash 低相似当成平台原创度通过。
- 不只显示“抗查重完成”，应显示哪些实质内容发生了变化。
- 不在容量不足时静默降低版本数或高比例复用；应让用户确认策略。
- 不让前端硬编码切片账号，最终账号和水印必须来自后端计划。

## 5. 下一阶段建议的算法方向

建议按以下顺序改造，先保证“一个版本值得发”，再考虑批量版本：

1. **建立内容级相似模型**：画面 + ASR 文本 + 原声音频 + 集覆盖 + 同源码比例，形成可解释风险评分。
2. **增加跨账号和平台侧已知内容登记**：至少把本机两个账号的已上传成片纳入全局比较；平台已发表内容无法直接抓取时，必须明确把本地结果标为“平台风险未知”，不能标绿。
3. **将版本数量改为容量驱动**：独立剧情单元不足时减少版本，而不是用 90% 复用硬凑 8 版。
4. **让角度真正参与选段**：每个 angle 对应角色线、冲突目标、情绪阶段和允许使用的集/片段集合。
5. **引入实质性再创作层**：新旁白/解说、结构化字幕、重新讲述故事、授权 B-roll 或新音轨等。单纯滤镜、变速和水印只作为发布工艺，不作为原创性保证。
6. **同剧同账号限制重复发布**：默认一剧一主版本；只有内容结构显著不同且风险检测通过后才生成额外版本。
7. **把门禁结果写进 EDL 和报告**：每个版本保留画面、文本、音频、来源覆盖和风险原因，供 Web 页面直接读取。
