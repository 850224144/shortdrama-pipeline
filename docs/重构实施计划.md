# 短剧工坊阶段一基础重构实施计划

> 创建日期：2026-11-07
> 适用范围：本地单机 Windows 工具，不对外开放
> 原则：保持现有业务行为不变，按步拆独立提交，每步全量测试通过 + 主链路冒烟通过后再进下一步；每步独立可回滚。

## 一、背景与目标

本计划来自 2026-11-07 命令行对话梳理的四阶段重构清单，经裁剪后**本轮只实施阶段一「基础重构」**。阶段二（Celery 队列）、阶段三（前端工程化）、阶段四（高级特性）本轮不做，仅在第六节记录裁剪结论与升级触发条件。

阶段一目标：降低技术债，不改功能、不改路由契约、不改 SQLite 表结构。具体五件事：

1. 配置外置：硬编码路径与参数收口到配置文件，消除模块对 `processor.CONFIG` 的反向依赖。
2. 日志结构化：统一日志入口与字段，支持按剧名 / 账号 / 任务 / 批次过滤。
3. 队列基类抽象：上传、切片两套队列抽公共状态机，补重试上限与超时熔断。
4. 后端 Blueprint 拆分：`app.py` 路由按域拆分，主文件只留启动与注册。
5. 测试分层：单元测试与集成测试分离，补公共 fixture，新代码有测试兜底。

## 四、阶段一任务清单（按顺序执行）

### 4.1 配置外置

**现状问题**：`CONFIG` 定义在 `processor.py`，路径与业务参数混在一起；多个模块反向 `from processor import CONFIG`；换机器必须改代码。

**做法**：
1. 新增 `webapp/config.py`：`Config` 单例，对外保留与现有 `CONFIG.get(key, default)` 同构的读取接口，调用方零改动。
2. 配置来源分层：
   - `.env`（机器相关，环境差异大）：素材根目录、输出 / 数据 / 日志 / 临时目录、ffmpeg / ffprobe / BaiduPCS-Go / ASR 脚本 / scripts 目录路径、AI 密钥。
   - `config.yml`（业务参数，嵌套结构）：`download / edl / duration / causal_check / upload / scene_snap / quality / resource` 各段。
   - 加载优先级：环境变量 > `config.yml` > 内置默认值；`health.py` 现有的 `SHORTDRAMA_*` 覆盖逻辑并入 `config.py`，不重复维护。
3. 提供 `.env.example`（变量名、用途、是否必填）与 `config.yml.example`（默认值与注释），纳入版本控制；真实 `.env` 不提交。
4. `processor.py` 改为从 `config.py` 导入配置；其余模块的 `from processor import CONFIG` 改为从 `config.py` 导入，解除 processor → 配置、配置 → processor 的循环依赖风险。
5. 路径类配置统一为 `pathlib.Path` 或字符串常量二选一，保持与现有调用方式兼容；嵌套段读取缺省时给默认值，避免 `KeyError`。

**涉及文件**：新增 `config.py`、`.env.example`、`config.yml.example`；改动 `processor.py`、`app.py`、`upload_manager.py`、`content_fingerprint.py`、`artifact_cleanup.py`、`health.py`。

**验收标准**：
- 代码中不再出现裸绝对路径硬编码（路径类全部来自配置）。
- 换机器只改 `.env` / `config.yml`，不改 Python 代码。
- 现有全部 `CONFIG.get(...)` 调用行为不变，全量测试通过；`/api/health` 检查项照常给出 ok / degraded / failed。
- 缺省配置下开箱可跑（默认值与现状一致）。

**回滚方式**：`config.py` 为独立新增模块；回滚时恢复 `processor.py` 的 `CONFIG` 定义与各处 import，配置文件不参与运行，可直接保留。

**风险**：中低。重点在嵌套 dict 合并的默认值兜底，以及 import 调整顺序，避免循环导入。

### 4.2 日志结构化

**现状问题**：两套日志实现（`processor.Logger` 文件+推送、`UploadManager._log` 内存+print）；无标准 logging 初始化；字段缺任务 / 账号 / 批次维度，出问题要对比多份日志。

**做法**：
1. 使用标准库 `logging` + JSON formatter（**不引入 structlog**，零新依赖）；建立统一日志入口。
2. 保留现有两类输出：按天文件落盘、socketio `log_update` 向前端推送；前端推送条目结构不变，避免现有日志页异常。
3. 日志固定字段：`timestamp / level / drama_name / account / task_id / batch_id / stage / message`，其余上下文走 `extra` 挂载。
4. 改造关键节点：上传 / 切片的入队、开始、完成、失败、重试、停止；下载 / 渲染 / 后处理阶段切换。
5. `UploadManager._log` 收口到统一入口，去掉独立 `print`；旧 `Logger` 类保留为兼容层过渡。

**涉及文件**：新增日志配置模块；改动 `processor.py`（`Logger`）、`upload_manager.py`、`cut_manager.py`、相关 manager 调用点。

**验收标准**：
- 日志可按 `drama_name / account / task_id / batch_id` 检索过滤。
- 前端实时日志页展示与推送行为不变；全量测试通过。
- 关键失败路径日志带足定位字段（任务 id、账号、剧名、阶段、错误信息）。

**回滚方式**：统一日志入口可切回旧 `Logger` / `_log`；兼容层保留期间切换成本低。

**风险**：低。注意文件写入与 socketio 推送的顺序与加锁，避免前端出现重复或乱序条目。

### 4.3 队列基类 `BaseQueueManager`

**现状问题**：上传、切片两套队列各自实现暂停 / 恢复 / 停止 / 状态快照；公共状态重复；缺统一的任务重试上限与超时熔断。`JobStore` 已是 SQLite 持久化层，基类应基于它抽象，不另起一套存储。

**做法**：
1. 新增队列基类（建议 `webapp/base_queue.py`）：抽象公共状态机——队列、当前任务、暂停 / 恢复 / 停止、完成集合、失败集合、状态快照；持久化读写统一走 `JobStore`；模板方法 `_execute_task(task)` 留给子类实现。
2. 公共能力收口到基类：
   - 任务级重试次数上限：`retry_count` 达上限标 `failed`，不再自动重试。
   - 单任务超时熔断：超时停止当前任务，按现场归位 `pending`（可重跑）或 `failed`（保留错误信息）。
   - 僵死检测复用切片现有心跳思路，统一到基类约定。
3. `UploadManager`、`BatchCutManager` 继承基类，各自实现执行钩子；账号切换、processor 调用等差异保留在子类，**不强行统一执行流程**。
4. **本轮不引入 Celery / Redis**（裁剪结论见第六节）。

**涉及文件**：新增 `base_queue.py`；改动 `upload_manager.py`、`cut_manager.py`；`job_store.py` 原则上不改结构，如需补字段走幂等 `ALTER TABLE`（对齐 R3 做法）。

**验收标准**：
- 两个 manager 共用基类，队列 / 暂停 / 停止 / 快照等重复代码消除。
- 重启恢复、心跳归位行为不变；`test_upload_recovery.py`、`test_cut_persistence.py`、`test_cut_reconcile.py` 等现有用例全部通过。
- 重试上限、超时熔断有对应单元测试覆盖。

**回滚方式**：基类是抽象层，独立 commit；回滚后两个 manager 退回各自原实现即可。

**风险**：中。两者执行模型不同（上传走 worker 线程，切片走 processor + 心跳），基类只抽公共状态与公共能力，不把执行流程压成一套。

### 4.4 Blueprint 路由拆分

**现状问题**：`app.py` 1233 行、60+ 路由挤在单文件；改一个接口要在大文件里翻找；业务调用与路由参数校验混在一起。

**做法**：
1. 按业务域拆 Flask Blueprint：`process`（状态 / 历史 / 日志 / process / stop / demo / cleanup-logs）、`upload`、`cut`、`archive`、`login`、`baidupcs`、`cleanup`、`files`。
2. `app.py` 只保留：Flask / SocketIO 创建、配置加载、Blueprint 注册、socketio 事件绑定、启动钩子、错误处理器。
3. 路由函数只做参数校验与 JSON 返回；业务调用下沉到既有 manager / service，不在路由里堆逻辑。
4. manager 实例与 socketio 依赖通过构造注入，注意 import 顺序，防止循环依赖。

**涉及文件**：新增 `webapp/api/` 下各 Blueprint 模块；改动 `app.py`。

**验收标准**：
- `app.py` 降到 200 行以内。
- 60+ 路由的路径、HTTP 方法、返回结构保持不变；全量测试通过，前端五个 tab（实时日志 / 历史记录 / 批量上传 / 批量切片 / 剧级档案）手动冒烟正常。

**回滚方式**：按 Blueprint 独立 commit，可逐个 revert；主文件改动与拆分模块分离提交。

**风险**：中低。主要在依赖注入顺序与循环 import；拆分前后路由契约必须逐一对齐。

### 4.5 测试分层

**现状问题**：41 个测试文件单元 / 集成混排；根目录 8 个手动冒烟脚本与 pytest 用例混在一起；无公共 fixture；新代码缺测试兜底。

**做法**：
1. 目录分层：`tests/unit/`（纯函数：配置加载、队列状态机、内容指纹、EDL / 打分、质量门禁，不依赖浏览器 / 真实素材 / ffmpeg）、`tests/integration/`（起 Flask 走完整链路）。
2. 根目录 8 个手动脚本移到 `tests/manual/` 或 `scripts/`，加说明，不进 pytest 默认收集。
3. 新增 `conftest.py`：公共 fixture（内存 `JobStore`、测试配置、Flask test client）。
4. 为 4.1 配置加载、4.3 重试上限 / 超时熔断补单元用例；本轮不设覆盖率硬指标，先保证新代码有测试。
5. CI 流水线本轮不建；本地用 Python311 跑：`pytest tests/unit` 快速反馈、`pytest tests/integration` 完整验证。

**验收标准**：
- `tests/unit/` 可秒级跑完，不依赖外部进程与素材。
- 现有用例一条不丢，全量绿；手动脚本仍可独立运行。
- 4.1 / 4.3 新增逻辑有对应单测。

**回滚方式**：以文件移动为主，revert 提交即可恢复原位置。

**风险**：低。注意移动测试文件后修正 `sys.path` 与 import。

## 六、后续阶段裁剪结论（本轮不实施，仅记录触发条件）

| 阶段 | 本轮结论 | 升级触发条件 |
|---|---|---|
| 阶段二 Celery + Redis | **不做**。当前单机 Windows、单人工具，`JobStore` SQLite + 线程队列 + 心跳归位已覆盖重启恢复；重试与超时在基类内补即可 | 出现多机跑批、任务需跨进程独立常驻、需要优先级队列或任务依赖调度等真实需求时再评估 |
| 阶段三 Vite + Vue3 / Pinia | **不做**。前端功能已跑通，单人维护，组件化收益有限；本轮最多评估 CSS / JS 抽离到 `static/` 的轻量动作 | 前端演进到多人维护，或出现复杂多视图状态共享时再上框架 |
| 阶段四 批次进度聚合 | 列入后续 backlog，本轮不做 | 批量上传 / 切片需要整批进度视图时实施 |
| 阶段四 可操作错误 | 列入后续 backlog，本轮不做 | 前端错误提示需要带动作按钮（如「重新登录」）时实施 |
| 阶段四 Prometheus + Grafana | **不做**。本地单机无多实例监控需求，结构化日志 + `/api/health` 足够 | 服务对外或多实例部署后再评估 |
| 阶段四 偏好持久化 | 后续仅用 `localStorage` 保存选剧状态，不上后端偏好 API | 选择状态需要跨设备 / 跨浏览器同步时再做后端接口 |

## 七、明确不做项（本地版本排除）

- 安全加固：用户鉴权登录、CSRF 防护、限流、HTTPS 证书。
- 部署优化：Gunicorn / Nginx、systemd 开机自启、生产服务器配置。
- 分布式多机调度、Celery / Redis 任务队列。
- 前端框架（Vue / React / Svelte）与构建链。
- structlog 及其他日志栈、监控告警栈、CI 覆盖率门禁。
