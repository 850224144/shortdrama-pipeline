# 分支管理与自动合并规则

## 一、分支定义

| 分支 | 角色 | 说明 |
|---|---|---|
| `main` | **发布分支** | 稳定、已验证的代码；只接受来自开发分支的 ff-only 合并 |
| `codex/pipeline-reliability` | **开发分支** | 所有开发/增强/修复在此分支进行；验证通过后自动合并到 main |

## 二、开发与验证流程

1. 在开发分支 `codex/pipeline-reliability` 开发（提交）。
2. **验证门禁**：本地全量测试必须全绿
   ```bash
   cd webapp
   C:/Users/86159/AppData/Local/Programs/Python/Python311/python.exe -m unittest discover -s tests -p "test_*.py"
   ```
   期望输出 `OK`（1 项冒烟默认跳过属正常）。
3. 验证通过后**推送到开发分支**：
   ```bash
   git -c http.proxy= -c https.proxy= push origin codex/pipeline-reliability
   ```
4. push 触发 GitHub Actions（`.github/workflows/auto-merge.yml`）**自动合并**开发分支到 `main` 并推送。

## 三、自动合并机制（GitHub Actions）

- 触发：push 到 `codex/pipeline-reliability`。
- 动作：`git merge --ff-only` 合并到 `main` → `git push origin main`。
- **安全边界**：
  - 仅 **ff-only**：main 有并发新提交时合并失败（报错，不强制改写历史），需人工处理。
  - `concurrency` 串行化，防并发推送竞争。
  - 远程执行，不触碰本地任何文件。
- 失败处理：Actions 运行失败（如 main 有新提交、push 被保护拒绝）→ 手动 `git fetch origin && git merge --ff-only origin/codex/pipeline-reliability` 解决。

## 四、本地兜底

远程 Actions 不可用时（网络/权限问题），用本地脚本完成同样的"验证→合并→推送"：

```bash
bash scripts/merge_main.sh
```

与 Actions 相同的门禁：测试全绿才合并；ff-only；绕过代理推送。

## 五、对进行中任务的影响

**自动合并不影响任何进行中的任务**：

- **素材下载**（如 `BaiduPCS-Go download ... --saveto E:\短剧素材\...`）：下载目标在 git 仓库外（E 盘），仓库内 `素材/` 目录被 `.gitignore` 忽略，合并只更新 git 跟踪的代码文件——不触碰下载进程及文件。
- **webapp 服务**（`:8765`）：合并更新代码文件，运行中的服务进程已加载旧代码，不受影响；下次重启加载新代码。
- **渲染/上传**：同理，运行中的进程不受影响。

唯一注意：**本地**合并（`scripts/merge_main.sh`）需要工作区相对干净（未提交改动会跟随切换，如与目标分支无差异则无冲突）。远程 Actions 合并无此限制。
