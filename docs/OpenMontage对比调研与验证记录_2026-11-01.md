## 一、结论与证据边界

OpenMontage 值得作为剪辑审核和质检的设计参考；目前证据不足以证明它比现有短剧混剪链路剪得更好，也不足以决定直接集成或替换。其 Clip Factory 的公开定义主要针对单部长视频提取多个独立片段，并非明确针对跨多集短剧的剧情重组。上游把该流水线标记为 beta。

本记录区分三种证据：

1. **本项目代码核查**：在当前工作区读取实际代码；不代表每个能力已在真实素材上验证。
2. **上游公开设计**：通过官方仓库读取流水线定义及指导文件；部分是给智能体的工作要求，并非已运行验证的确定性功能。
3. **本机合成冒烟**：实际运行现有测试生成的两段 34 秒合成视频，验证本项目渲染和基本质量门禁；不代表真实短剧画质或剧情效果，更不是双系统对比。
4. **上游合同测试**：在固定提交上运行不依赖付费模型的 pipeline/checkpoint/Backlot 合同测试，验证清单、审批门禁和检查点行为；不等于运行了上游完整创意流水线。

## 二、逐项比较

| 领域 | 当前项目代码证据 | OpenMontage 公开证据 | 判断 |
|---|---|---|---|
| 素材与任务 | `webapp/processor.py` 支持多集扫描、集号解析；`webapp/cut_manager.py` 提供持久队列和重启恢复 | Clip Factory 清单描述单个长视频分成多个短视频，属于 beta | ；上游多集能力未当前项目在多集和视频号工作流上更贴合实测 |
| 候选片段 | `processor.py` 有台词关键词和 LLM 高光窗口、导演方案及多维审稿；导演审稿失败可放行 | 指导文件要求按钩子、连贯性、价值、节奏和平台适配排序，并记录候选及选择/拒绝原因 | 已有基础；值得补充候选清单、理由和可核验的来源覆盖度，不应把 LLM 得分当作质量保证 |
| 方案审批 | 本项目保存 `edl_config_v*.json`，主要供渲染、报告和续跑；当前代码未见完整的渲染前人工修改与批准门禁 | 流水线清单中 script、scene_plan 等阶段默认要求人工审批；Backlot 展示流水线产物 | 优先借鉴流程；审核 UI、审批持久化和阻止未批准渲染需单独设计验证 |
| 镜头边界 | 当前项目已有 ffmpeg 场景检测和起点吸附 | 上游指导以转写为主、场景检测为候选边界的辅助检查 | 不是从零补场景检测；重点验证中文对白的切点、人物和上下文连续性 |
| 质量检查 | `delivery_quality.py` 检查文件、音视频流和时长；`qc_report.py` 审计黑帧、响度和转写句内切断；渲染器已有响度标准化 | 上游 README 描述 ffprobe、抽帧、音频、字幕及成片自检；Clip Factory 指导要求逐输出核对 | 当前已有基础但 QC 报告不是门禁；上游效果未经实测，不宜断言其检测准确率或覆盖完整性 |
| 单个版本失败 | 现有生成/续跑有逐版本处理和系统性错误 fail-fast | 上游指导逐输出作为作业、单项失败记录并尽量继续 | 两者都考虑部分失败；应保留当前对系统性故障的 fail-fast，避免盲目继续 |

## 三、核查中发现的当前风险

1. **QC“无黑帧”可能混淆未检测和检测通过**。`webapp/qc_report.py` 的 `check_black_frames` 遇到缺文件或异常会返回空列表；`processor.py` 以空列表输出“无黑帧段”。命令非零退出也未单独检查。应区分 `pass / warning / unknown`，避免检测失败被展示成通过。同理，缺少转写时不能表述为已确认没有句中切断。
2. **基本媒体门禁的异常兜底放行**。`processor.py` 的 `_validate_delivery_media` 在门禁自身抛异常时返回 `ok=True`。建议至少显示“未验证”，并在预设策略中区分阻止交付与需人工确认。
3. **Windows 输出编码影响渲染子进程启动**。本机合成冒烟在默认输出编码下，`render_generic.py` 输出 emoji 日志触发 `UnicodeEncodeError: 'gbk' codec can't encode`；传入 `PYTHONUTF8=1` 后通过。尚未证明每种部署入口都受影响，应另设针对性的子进程编码回归测试。

## 四、本机验证记录

执行现有 `webapp/tests/test_render_smoke.py`：该测试用 ffmpeg 合成两段 1080×1920、各 34 秒且带音轨的测试视频，按手写 EDL 调用本项目渲染，最后检查时长、音视频流与分辨率。

- 默认环境：**失败**，原因是渲染子进程的 GBK 输出编码无法打印日志中的 emoji；失败发生在正式渲染前。
- 设置 `PYTHONUTF8=1`：**1 passed，33.62 秒**。
- 此结果仅覆盖合成素材的本项目渲染链路，不含真实短剧、ASR、OpenMontage、视频号或人工剧情评价；没有采集显存峰值、成本和对方执行时间。
- 未发送或上传用户素材，也未触发平台发布或清理。

## 五、隔离审阅结果与比较边界

上游已克隆到独立临时目录，没有修改本项目，也没有直接复制其代码。固定提交的核心依赖为 Python 3.10+、FFmpeg，完整安装还会拉取 Remotion/Node、Piper 及可选模型依赖；实际创意生产依赖外部 LLM/媒体 API 或本地 GPU 模型。

在该提交上执行 `tests/contracts/test_pipeline_catalog.py` 与 `tests/contracts/test_backlot_contract.py`，结果为 **55 passed**。这些测试确认了三件值得借鉴的事实：

1. 流水线清单和阶段产物有 schema/审批约束，不靠口头约定。
2. 受人工门禁保护的阶段不能直接写成 `completed`，除非记录明确批准。
3. 被替代的检查点进入历史存档；Backlot 从项目文件推导状态，并限制为本地访问。

这不证明上游剪辑效果更好。Clip Factory 仍是 beta，核心定义为“单个长视频产出多条独立短片”；本项目是“多集短剧跨集重组 + 视频号草稿箱”，两者不是等价任务。OpenMontage 的价值主要是生产治理和审核体验，而不是直接替代现有下载/ASR/渲染/上传链路。

完整上游创意运行未执行：需要额外安装 Remotion/Piper/模型依赖并可能产生外部费用；当前调研不需要为了验证清单行为而触发付费模型。真实素材已经用于验证本项目链路，双系统同素材成片比较仍需在明确费用和审批后另行执行。

### 可复现实验方案

1. 由用户指定一部有权处理的短剧及 3–5 集素材，确认只做本地处理；复制到独立测试目录，不使用生产输出目录。优先选择已有中文字幕的素材，禁止默认烧录重复字幕。
2. 固定双方版本、输入素材校验和、输出画幅、目标时长、版本数量、是否使用云模型、费用上限和人工审批步骤。保留双方各自适用的真实流程，不假装两种不同的选段任务完全等价。
3. 如 OpenMontage 只能接收单文件，先记录并验证该限制；有必要时用无损或明确标记的拼接副本输入，并保存集号到拼接时间的映射；这不是原生多集支持。
4. 在隔离目录产出方案与短样，记录输入输出、开始结束时间、峰值 GPU 显存（可用时）、CPU/RAM、模型及实际外部费用。无可用指标标为“未测”。
5. 人工盲评钩子清晰度、剧情可理解性、上下文连续性、句子切断、版本差异和修改便利性；给出片段编号、证据与评分，不用未经验证的“爆款率”衡量。
6. 采集黑帧、静音、响度、分辨率和时长检查结果，分别标注通过、异常、未检测；检查结果需抽样人工确认。

## 六、建议推进顺序

1. ✅ **小范围可靠性修正已完成（2026-11-01）**：QC 已区分 `pass/warning/unknown`；媒体门禁无法验证时 fail-closed；ASR/渲染子进程强制 UTF-8；旧高光缓存会归一化到最短片段。
2. ✅ **只读候选方案预览已完成（2026-11-01）**：`/api/cut/preview` 与切片页展示版本、片段来源、入出点、钩子、时长、选段理由和产物状态，不改变渲染/上传流程。
3. **审批/修改闭环待做**：明确定义草稿、已批准、渲染中、已过期版本等状态，避免用户审核后 EDL 被修改却仍沿用旧批准。建议下一阶段先做审批状态模型，再做渲染前门禁。
4. **暂不直接集成上游代码**：先核实其 AGPL-3.0 许可证对具体部署方式的影响与第三方依赖；独立研究设计也不等于可以复制受保护代码。实际集成前应完成许可证审查。
