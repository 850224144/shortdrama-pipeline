# 短剧工坊可靠性优化设计与实施计划

> 分支：`codex/pipeline-reliability`  
> 创建日期：2026-10-31  
> 原则：保持现有单机 Windows 工具形态，优先提高可恢复性、状态一致性和可观测性；所有阶段均以自动化测试或可重复冒烟检查验收。

## 一、目标与范围

当前流水线已经具备下载、ASR、EDL 渲染、后处理、交付报告、上传队列和清理能力。本轮优化不重写核心媒体算法，重点解决以下问题：

1. 停止请求不完整：主处理入口仍存在假停止，下载阶段也不能及时取消。
2. 并发入口割裂：单消息处理、批量切片、自动清理之间没有共享资源闸门。
3. 切片队列不持久：服务重启后 pending/cutting 任务丢失。
4. 状态来源过多：JSON、多个 SQLite 表、文件标记和内存对象可能发生漂移。
5. 批量上传不是原子操作：前端逐条提交可能产生半批次。
6. 配置和启动检查分散：绝对路径、二进制、账号、磁盘和编码器问题通常在任务跑到一半才暴露。
7. 缺少结构化阶段数据和媒体质量门禁。
8. 前端存在未转义 HTML 拼接和完成通知不足。

不在本轮范围：重做剪辑业务规则、替换 ffmpeg、实现远程多机调度、实现网站账号密码自动登录。

## 二、总体设计

### 2.1 统一任务与取消上下文

新增轻量任务上下文，包含：

- `job_id`：跨日志、数据库和 API 的稳定标识。
- `cancel_event`：沿用 `threading.Event`，所有长任务阶段统一检查。
- `stage(name, progress)`：记录阶段切换和耗时。
- `check_cancelled()`：触发统一的 `JobCancelled`。

主消息处理、批量切片和长子进程都接入同一取消语义。停止成功后不再直接返回成功，而是返回当前阶段和 `stopping=true`；worker 完成清理后状态变为 `cancelled/stopped`。

### 2.2 全局资源闸门

新增进程内执行闸门：

- `pipeline`：下载 + ASR + EDL 编排，同一时刻只允许一个。
- `asr`：ASR 任务并发 1。
- `render`：GPU 渲染并发 1。

闸门使用非阻塞获取，冲突时返回明确的 409/队列状态，不静默启动第二套流水线。

### 2.3 持久化任务库

在统一数据目录中增加 SQLite 任务库，最小表结构：

```sql
CREATE TABLE jobs (
  id TEXT PRIMARY KEY,
  job_type TEXT NOT NULL,
  status TEXT NOT NULL,
  stage TEXT,
  progress INTEGER DEFAULT 0,
  params_json TEXT,
  result_json TEXT,
  error TEXT,
  cancel_requested INTEGER DEFAULT 0,
  created_at TEXT,
  updated_at TEXT,
  started_at TEXT,
  finished_at TEXT
);

CREATE TABLE job_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  job_id TEXT NOT NULL,
  level TEXT,
  event TEXT,
  message TEXT,
  metadata_json TEXT,
  created_at TEXT
);
```

状态机：`pending -> running -> completed|failed|cancelled`，暂停/停止通过独立信号表达，避免把控制信号混入业务结果。

### 2.4 状态对账

以任务库、档案库和上传库作为权威数据，JSON/文件标记作为兼容层。启动时执行：

1. `running` 且超过心跳窗口的任务改为 `pending`，清空运行时字段。
2. 切片完成但成片不存在时改为 `failed` 或 `pending`，不错误阻止重切。
3. 磁盘存在交付成片但任务仍 pending 时，记录为可恢复现场，交由用户确认。
4. 上传记录恢复逻辑保持幂等。

### 2.5 批量上传原子化

新增 `POST /api/upload/batches`：

- 服务端校验剧名、账号、版本、文件存在性和重复任务。
- 在一个事务内创建批次和所有上传记录。
- 返回 `accepted`、`duplicates`、`missing`、`rejected` 明细。
- 前端只提交一次，避免半批次已入队。

### 2.6 配置与健康检查

新增统一配置加载层：

- 支持环境变量覆盖路径和密钥。
- 启动时验证目录、ffmpeg/ffprobe、ASR、BaiduPCS-Go、磁盘和 NVENC 探测。
- 新增 `/api/health`，区分 `ok/degraded/failed`，返回每项检查的结果和建议。
- README 与运行配置保持同源描述。

### 2.7 性能、质量与可观测性

- 缓存 ASR transcript、ffprobe 结果和导演方案，以内容指纹失效。
- 每个阶段记录开始/结束、耗时、退出码和错误类别。
- 渲染完成后检查文件存在、时长、音视频流，阻止 0 字节和残缺文件进入交付。
- 前端展示当前阶段、进度、开始时间、错误和最近事件。

### 2.8 代码结构

渐进抽取，不在单一改动中重写：

- `job_store.py`：持久化任务和事件。
- `job_runtime.py`：任务上下文、取消和资源闸门。
- `cut_manager.py`：批量切片状态机。
- `delivery_quality.py`：媒体质量门禁。
- 后续可从 processor 中继续拆出下载、ASR、渲染和交付服务。

## 四、实施顺序与回滚

顺序：R1 -> R2 -> R3 -> R4 -> R5 -> R6 -> R7 -> R8。

每项完成后：

1. 更新本表状态为“已完成”，补充实现文件和测试证据。
2. 运行该阶段定向测试。
3. 运行完整 `webapp/tests` 回归。
4. 如有兼容性风险，保留旧接口和旧数据迁移路径；数据库变更只做 `CREATE IF NOT EXISTS` 或显式列迁移。

## 五、完成记录

### R1 统一任务上下文、真实停止和全局资源闸门 ✅

- 新增 `job_runtime.py`：`JobContext`、`JobCancelled`、`ExecutionGate`。
- 新增 `process_job.py`：主处理单任务控制器，`/api/stop` 发出真实取消信号并返回 `202 + stopping`。
- `/api/process`、批量切片共享 `pipeline` 闸门，冲突入口返回明确 409。
- ASR 与渲染分别使用独立资源闸门。
- 下载重试、转存、主下载命令接入取消；ASR、EDL 渲染沿用可终止进程树机制。
- 停止属于 `cancelled`，不写失败状态，不继续重试。
- 测试：`test_job_control.py`、`test_cut_cancel.py` 等定向 22 项通过；全量 131 项通过。

### R2 切片队列持久化 ✅

- 新增 `job_store.py`：`JobStore`，`data/jobs.db`，表 `jobs` + `job_events`（`CREATE IF NOT EXISTS`，WAL + busy_timeout，UPSERT 更新保留 started_at/finished_at）。
- `BatchCutManager` 接入存储：入队/开始/完成/失败/停止每次迁移同时写库；停止信号用 `cancel_requested` 独立表达，不混入业务结果；任务 `id` 改为稳定字符串（uuid）。
- `_recover()`：重建 manager 时从库恢复全部切片任务，`cutting`（崩溃现场）归位为 `pending`，completed/failed 保留视图一致；停止任务持久化为 pending，重启后可继续。
- `clear_queue` 同步删库；`add_to_queue` 恢复后仍去重。
- 新增 `GET /api/cut/events`（`job_id`、`limit` 可选）查询持久化事件；任务级事件（入队/开始/完成/失败/停止）+ 队列级事件均落库。
- 测试：`test_cut_persistence.py` 定向 8 项（恢复 pending、崩溃归位、停止后续跑、完成/失败保留、resume 透传、事件查询、清库、去重）；全量 139 项通过。

### R3 状态对账 ✅

- `jobs` 表新增 `heartbeat_at` 列（`CREATE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN` 显式迁移，幂等）；`JobStore` 新增 `touch_heartbeat()` / `stale_jobs()`。
- `BatchCutManager` 新增心跳线程：切片运行期间每 5s 刷新当前任务 `heartbeat_at`；`HEARTBEAT_WINDOW=30s` 判僵死。
- `reconcile()`（幂等，可启动时 + 手动调用）：
  1. 心跳过期的 `cutting` 任务（进程僵死）→ 归位 `pending`，清空 `started_at`/`cancel_requested`/`heartbeat`；
  2. `completed` 但输出目录无 `_去重版.mp4`/`edl_config` → 标 `failed`（可重切，不阻止）；
  3. `pending` 但磁盘已有成片 → 打 `recovered` 标记（不改状态），交用户确认。
  - 每个变更写 `reconcile_stale`/`reconcile_missing`/`recoverable_scene` 事件，返回结构化报告。
- app.py 启动时跑 `_startup_cut_reconcile`（后台线程，日志输出报告）；新增 `POST /api/cut/reconcile`。
- 上传库恢复逻辑保持幂等（既有 `test_upload_recovery.py`）；档案库是来源追踪层，非工作队列，不入对账范围。
- 测试：`test_cut_reconcile.py` 定向 7 项（僵死归位、新鲜不误杀、缺成片标失败、有成片不动、可恢复现场标记、幂等、心跳刷新）；全量 146 项通过。

### R4 原子批量上传 ✅

- `UploadManager.add_batch(items)`：一次校验（必填/文件存在/重复 pending+uploading）+ **一个事务** 插入全部通过校验的记录（任何插入失败整体回滚），返回 `{accepted, duplicates, missing, rejected, ids, accepted_details}` 结构化明细。
- 新增 `POST /api/upload/batches`：请求 `{items: [...], batch_id}`，服务端一次建批；成功条目按 `accepted_details` 幂等登记批次元数据（供清理计划器聚合）。
- 前端 `startUpload()` 改为**一次请求整批提交**（收集全部条目 → 单次 `/api/upload/batches`），替换逐版本 `/api/upload/add` 循环；跳过的重复/缺失/校验失败以明细提示，不再逐条半提交。
- 测试：`test_add_batch.py` 定向 6 项（整批创建、缺失上报、重复明细、缺字段拒绝、空数组 noop、混合场景无半批次）；全量 152 项通过。

### R5 配置与健康检查 ✅

- 新增 `health.py`：
  - `apply_env_overrides(CONFIG)`：`SHORTDRAMA_*` 环境变量覆盖 ffmpeg/ffprobe/下载目录/输出目录/数据目录/日志目录/BaiduPCS/ASR 脚本/脚本目录；未显式覆盖 ffprobe 时由 ffmpeg_dir 推导；幂等。

### R6 阶段指标与媒体质量门禁 ✅

- 新增 `delivery_quality.py`：
  - `probe_media(file_path, ffprobe_path)`：ffprobe JSON 读取流信息（streams/format.duration）。
  - `validate_media(file_path, min_duration, max_duration)`：拒收 文件不存在/0 字节/无视频流/无音轨/时长为 0/时长过短/时长过长；ffprobe 失败保守拒收；返回 `{ok, reason, size, duration, has_video, has_audio}`。
- processor `_run_render_one` 成功分支接入质量门禁（`_validate_delivery_media`）：产物不达标 → 记日志并返回 `(None, 'quality')`，**不进入交付**；门禁自身异常不阻断交付（避免误杀）。
- 阶段指标：`cut_manager` 终态事件（`cut_completed`/`cut_failed`/`cut_stopped`）携带 `metadata={duration_seconds, stage:'cut'}`（新增 `_elapsed_seconds`）。
- 测试：`test_delivery_quality.py` 定向 11 项（缺失/0 字节/无视频/无音轨/0 时长/窗口外/正常/probe 失败拒收 + `_run_render_one` 拒收→'quality'、通过→video）；`test_cut_persistence` 新增终态事件耗时 1 项；`test_cut_resume` 两处渲染测试 mock 质量门禁；全量 171 项通过。
